# 喵包小程序 B++ 流程

从 Remio A++ 提取适合微信小程序的协作规则。适用于喵包小程序及其词库联动，不继承 Remio 的分支、工具或发布环境约定。

## 仓库与基线

| 仓库 | 本地位置 | 负责内容 |
| --- | --- | --- |
| MeowBread_wechat | `/Users/zoichi/Desktop/喵包` | 小程序代码、界面、内置词库副本、资源及检查脚本 |
| MeowBread_database | `/Users/zoichi/Desktop/喵包词库` | 原始词库 JSON、索引、词库制作规则及源资源 |

- 当前两个仓库默认以 `main` 为任务基线；用户明确指定其他已有分支时，以该分支为准。任务完成后合并回原基线。
- 不自动建立 `develop` 或 `release/*`。以后需要区分开发与待发布版本时，再明确调整本规则。
- 仅修改一个仓库时，只在该仓库建立任务分支。跨仓库任务在两个仓库使用同名任务分支，各自提交、合并和核对远端。
- 两个仓库没有原子提交；跨仓库交付需记录各自的提交及联动状态。

## 开新任务

1. 读取本流程及相关模块、词库制作规则，核对当前分支、工作区和远程地址。
2. 获取相关远程引用，报告当前分支、未提交改动、目标基线、本地相对远端的领先或落后情况。
3. 工作区干净时，在目标基线执行 `git pull --ff-only origin [基线]`，随后创建 `zoichi/[任务简称]`。
4. 任务简称优先用简短中文，一个分支承载一个完整任务；同一任务的修正继续使用该分支。
5. 有未提交改动时先辨明归属：已明确属于本任务的改动可以由任务分支承接；已有用户改动要保留，不混入本次提交。不带着未提交改动直接拉取或合并，不擅自 stash、覆盖、清理或丢弃。

当前历史改动尚未提交时，可以补建任务分支承接，再按改动内容拆分提交，无需重做开发。补建前仍须核对工作区与基线，不能假称这些改动从最新远端开始开发。

## 开发与验证

- 改动保持在任务范围内，保护原有学习进度、用户设置和其他未提交修改。
- 词库原始数据在独立词库仓库维护；需要内置副本时通过同步脚本生成，避免手工维护两份不同内容。
- 修改词库前读取 `dictionary_maker/data_rules.md`；核对课程边界、字段、重点标记、干扰项及索引，只开放已有有效数据的课程。
- 小程序代码改动运行 `npm run check`；涉及 N1 词库、出题或进度联动时运行 `npm run check:n1`，按需要先运行 `npm run sync:n1`。
- 其他课程使用与其数据和行为对应的检查，不把 N1 检查当作所有词库的验收。
- UI 和交互改动在微信开发者工具编译后实际核对；说明模拟器验收与真机验收的区别。无法验证时报告具体缺口，不声称已验收。
- 检查本次差异并运行 `git diff --check`。将本次失败与已有网络404、环境警告分开说明；检查通过后不无故重复全量检查。

## 本地保存

「本地保存一下」表示：检查并暂存本任务文件，在任务分支完成中文 commit，不推送、不合并。

- 提交信息采用“动词 + 对象 + 具体改动”，一条提交说明一个清晰结果。
- 例如：`新增N1第一课词库与重点标记`、`增加课程重点词练习入口`、`调整N1教材封面比例与排序`。
- 跨仓库任务分别提交；必要时按开发环境、数据、功能拆分，保持可追溯。
- 不使用无差别 `git add .` 混入历史改动；排除 `.DS_Store`、临时预览、日志、凭据及个人开发工具配置。已有被跟踪的系统文件也不因此纳入提交。
- 检查暂存差异后再提交，报告分支、提交 hash、内容、检查结果和剩余改动。
- 「本地保存一下，然后按 B++ 继续下一步」同时授权本地提交和下述 Git 交付。

## 按 B++ 继续下一步

该指令授权交付当前任务到它的既定基线，不包含微信上传、提审或发布。

1. 确认任务已提交、必要检查通过，待合并的工作区干净；未提交时先按“本地保存”完成任务提交。
2. 说明即将推送的仓库和目标分支，随后继续执行，不重复询问已授权的同一步骤。
3. 切回目标基线，执行 `git pull --ff-only origin [基线]`。
4. 执行 `git merge --no-ff zoichi/[任务简称]`，合并信息为 `合并分支 zoichi/[任务简称] 到 [目标分支]`。
5. 验证合并结果；如更新带来相关代码变化，补做受影响检查。确认任务分支提交已成为目标分支祖先。
6. 只推送目标基线：`git push origin [目标分支]`。不推送个人任务分支，不使用 cherry-pick。
7. 使用 `git ls-remote origin refs/heads/[目标分支]` 再次读取 GitHub 远端 hash，与本地目标分支比对。
8. 仅在远端核对一致后，使用 `git branch -d` 删除已合并任务分支。

跨仓库时先完成两个仓库的检查与本地提交，再逐仓库交付。若小程序依赖远端新增词库，通常先交付词库并确认部署资源可用，再交付小程序；内置数据可离线使用时需在回执中说明。中途失败时准确报告已完成和未完成的仓库，不把部分成功称为全部交付。

## 异常处理

- 分支不存在、非快进更新、合并冲突、鉴权失败或归属不明的改动阻碍操作时，停止受影响的 Git 步骤并报告准确状态。
- 不自动 rebase、强推、重置或丢弃改动，不猜测相近分支，也不绕过冲突。
- 用户明确授权冲突处理后，可以保留双方意图进行解决，重新检查后继续。
- 权限或自动审批拒绝时，说明被拒绝的具体动作与原因，不假称已经完成。

## 部署与微信发布

- Git commit：本地保存代码；Git push：同步代码到 GitHub。
- 词库仓库推送可能触发已有 GitHub Pages 自动部署；推送前核对当前部署配置，涉及线上变化时说明影响。未检查部署结果前不称资源已上线。
- 微信开发者工具上传、体验版、提审及正式发布是独立步骤，按用户对具体步骤的授权执行。
- 发布前按实际依赖核对词库与封面资源、版本和真机表现；发布回执与 Git 交付回执分开。

## 交付回执

每个实际参与修改的仓库分别报告：

```text
B++ 交付回执
仓库：[仓库名]
任务分支：zoichi/[任务简称]
目标分支：[基线]
合并提交：[hash]
远程确认：origin/[基线] = [hash] ✓ / 未确认及原因
任务分支：[已删除 / 未删除及原因]
工作区：[干净 / 剩余改动及归属]
检查：[实际执行的检查及结果]
部署与发布：[未执行 / 实际完成步骤及验证结果]
```

本流程约束喵包开发；不自动提交现有改动，也不改变 Remio 的 A++ 约定。
